The 3 held-out sessions of 2026-10-03 have informed three decisions (Stages 1–3). They are no longer a clean test.

This run is the **clean confirmation** of the Phase 2 claims, on sessions that have never been used for any choice. Its numbers are the **primary** numbers in the paper. The LOBO and held-out results are supporting evidence.

Nothing is tuned, retrained or selected in this run.

## 2. New sessions

- **Number:** **5** new baseline sessions, all recorded before any evaluation is run.
- **Recording:**
  - same Gazebo world, robot, logger and code as the existing sessions;
  - teleop at moderate speeds (about ≤ 0.8 m/s and ≤ 1.0 rad/s, as for the held-out set), avoiding full speed while turning;
  - aim for 50–70 s each;
  - each session mixes straight segments and turns in both directions;
  - no session copies a training route exactly.
- **Acceptance check:** `final_analysis.py check-sessions`, run **before** `mark-test` and before any EKF or model output exists. A session is ACCEPTED if all of these hold:
  1. `odom`, `imu`, `ground_truth` and raw `cmd_vel` files exist;
  2. duration ≥ 45 s;
  3. **no actuator saturation:** 0 raw command samples are changed by the pipeline's own saturation model, `preprocess_data.saturate_cmd_vel` (F1, per-wheel limit on v ± ω·s). This is the "0 clipped" definition used for the held-out set. It is read from the **raw** `cmd_vel_<session>.csv`; the actuator-limited `cmd_vel_filtered` file is never used for this check, and if the raw file is missing the session is rejected. Max \|v\| and \|ω\| are printed for information only;
  4. the logger's health check passed (the session is in `good_sessions`).
- **Replacements:** a REJECTED session is replaced by a new recording, up to 3 replacements in total. Every rejected session is listed in the deviations log with its reason.
- **No exclusion after evaluation:** once `mark-test` has run, every accepted session is evaluated and reported, whatever its result.

## 4. Procedure (commands)

### 4.1 Freeze (before recording)

```bash
cd ~/ws_mobile
diff <(cd sensor_logs && sha256sum model_*.pt) <(cd fix_ws/models_D2 && sha256sum model_*.pt) && echo MODELS_MATCH
python3 -c "import json;print(sorted(json.load(open('sensor_logs/session_registry.json'))['good_sessions']))" > fix_ws/final_training_list.txt
cat fix_ws/final_training_list.txt
{ echo "# frozen $(date '+%F %T %Z')"; sha256sum sensor_logs/model_*.pt scripts/*.py fix_ws/PREREG_final.md; } > fix_ws/final_freeze.sha256
```

The freeze is only valid if `MODELS_MATCH` prints and the training list shows exactly 7 sessions.

### 4.2 Record, then accept

```bash
python3 ~/ws_mobile/scripts/final_analysis.py check-sessions S1 S2 S3 S4 S5
```

### 4.3 Mark as test, then verify that nothing changed

```bash
cd ~/ws_mobile
python3 scripts/evaluate_heldout.py mark-test S1 S2 S3 S4 S5
python3 -c "import json;print(sorted(json.load(open('sensor_logs/session_registry.json'))['good_sessions']))" | diff - fix_ws/final_training_list.txt && echo TRAINING_UNCHANGED
grep -v '^#' fix_ws/final_freeze.sha256 | sha256sum -c --quiet && echo FROZEN_OK
```

Both `TRAINING_UNCHANGED` and `FROZEN_OK` must print before the run.

### 4.4 Run, once

```bash
sudo systemctl mask --runtime systemd-oomd.service systemd-oomd.socket
sudo systemctl stop systemd-oomd.service systemd-oomd.socket
cd ~/ws_mobile && nohup python3 scripts/evaluate_heldout.py stage1 --name final --sessions S1 S2 S3 S4 S5 > results/final_run.log 2>&1 &
```

`--sessions` is required. Without it, the 3 old held-out sessions would be included too.

### 4.5 Analyse, then restore oomd

```bash
cd ~/ws_mobile && python3 scripts/final_analysis.py analyse --name final 2>&1 | tee results/final_analysis.log
sudo systemctl unmask systemd-oomd.service systemd-oomd.socket && sudo systemctl start systemd-oomd.service
```

If the run is killed for a procedural reason (OOM, power, closed terminal):

## 5. Confirmatory tests (primary claims)

**Units.** D3 mid-onset IMU-bias sessions are excluded from all tests below.
- **C1 (wins):** wins are counted **separately for each of the 7 LOBO models**, and the 7 counts are averaged. This is the rule used in Stage 1 (H2) and Stage 3, so the final number is directly comparable with 41.6/48. Each LOBO model is a deployable filter, and this counts how often a deployed model wins. As a descriptive extra, wins are also counted once per fault session on the 7-model mean RMSE.
- **C2, P1, P2 (effect sizes):** the unit is the **fault session**, as in FINDINGS §15. For each fault session, the LSTM RMSE is the mean over the 7 LOBO models.

**Sizes:** odom n = 5 × 16 = 80; IMU n = 80; no-fault n = 5.

**Effect-size method:**
- % change = 100 × (method RMSE − fixed RMSE) / fixed RMSE (negative = better);
- median over sessions;
- 95% bootstrap CI of the median (2000 resamples, seed 0).

| ID | Claim | Pass rule |
|---|---|---|
| **C1** | LSTM-adaptive EKF wins against the fixed EKF on more than half of odometry-fault evaluations, and more often than the χ² heuristic | odom wins vs fixed, counted per model and averaged over the 7 models: **> 50%** of odom fault sessions (> 40/80) **and > heuristic** wins |
| **C2** | The odometry improvement is a real reduction in error, not just a tie-break | median odom % change, LSTM vs fixed: **upper 95% CI < 0** |
| **C3** | The adaptation does not harm clean data | no-fault baselines, mean RMSE: LSTM **≤ 1% worse** than fixed (7-model mean) |

## 7. Reported without pass/fail

- **H0:** clean EKF RMSE per session.
- **H1:** fault validation, as an **integrity check**. It uses the same rule as Stage 1, scaled to n = 5: worst severity ≥ 1.05× baseline in ≥ 37/40 checks, and large delay > baseline in ≥ 9/10. If it fails, all results are still reported, with the failure flagged next to them.
- **Wins and effect sizes** by sensor × fault type, for both methods.
- **Cluster-bootstrap CI for C2**, resampling baseline sessions. This shows how much the fault sessions of one baseline depend on each other.
- **D1 gate and D3 mid-onset bias:** printed by `stage1`, descriptive only.
  - **D1 is not adopted on this data**, whatever its result.
  - D6 (the IMU fix) will need its **own** new sessions and pre-registration.
- **Dry run:** `final_analysis.py` was run on the already-used 3-session D2 table, to test the code only. Its output reproduced FINDINGS §12/§15 (odom 41.6/48 per model, 41/48 per session on the model mean; median −8.2%; no-fault +0.22%). It says nothing about the final result.

## 8. How results go into the paper

**C1–C3 all PASS:** the paper states that the Phase 2 odometry claims are **confirmed on new sessions**, quoting the final numbers as primary.

**Any of C1–C3 FAILS:**
- the claim is reported as **not confirmed**, with the final numbers;
- the held-out and LOBO numbers are not substituted;
- no re-recording, retraining or threshold change follows from it.

**P1 and P2** are reported as confirmed or not confirmed, either way. If P1 fails, the "IMU effect negligible" statement is replaced by the measured effect.

## 9. Known limitations (stated before the run)

- **Simulation only;** single training seed (42).
- **n = 5 baselines.** Fault sessions from the same baseline are not independent. The primary CI treats them as independent, for consistency with §15; the cluster CI is reported next to it.
- **Fault magnitudes are stress-test magnitudes,** not realistic sensor errors (FINDINGS §4).
